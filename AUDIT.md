# SentinelPay audit and remediation

Date: 16 November 2026. Scope: the working-tree application, shared library, dependency manifests/lockfile, deployment configuration, legacy Solidity contracts, and historical Rust workspace. This is a source and local execution audit, not an independent security certification or a production penetration test.

## Product and architecture

SentinelPay is a merchant USDC invoicing application on Solana. A merchant proves control of a Solana wallet, creates an invoice, and shares a separate customer checkout. The server fixes the amount, mint, network, recipient, and expiry. Customers sign transactions; funds go to the merchant's wallet. Finalized RPC receipts, rather than browser state, determine whether an invoice is paid.

The reserve assistant uses actual wallet balances and merchant-supplied operating expenses, minimum reserves, and allocation limits. It is a deterministic policy engine. Optional Jupiter swaps support paying an invoice from another token and separately acquiring or selling a configured treasury token. These features do not provide identity verification, a yield guarantee, automatic issuer redemption, or autonomous wallet custody.

The Next.js server proxies supported API calls to Express using a private credential. Express stores sessions, merchants, invoices, payment attempts, treasury trades, and audit events in PostgreSQL. PGlite is a local development/test fallback. The Solidity contracts are a separate HashKey experiment. The Rust directory contains workspace metadata without program sources; neither secures the active checkout.

## Findings and changes

| -------- | --------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Critical | A valid signing keypair and a production environment export were tracked.                                             | Removed their working-tree files, expanded ignore rules, and added a source secret scan. **External revocation/authority review and historical copies remain unresolved.**                                                                                                                                    |
| Critical | Client-supplied payment state and unchecked confirmation errors could produce false success.                          | Added server-owned invoices and finalized receipt verification of the expected payer, prepared blockhash, invoice memo/reference, token mint/decimals, merchant account ownership, credited amount, and transaction error state.                                                                              |
| High     | Ethereum authentication and address normalization conflicted with Solana wallets.                                     | Replaced SIWE/JWT code with native Ed25519 verification, exact origin-bound single-use challenges, opaque revocable sessions, and case-sensitive wallet/signature storage. | High     | Client discounts and fallback recipient configuration could change payment meaning.                                   | Removed the discount toggle, always-ready configuration, arbitrary merchant recipient, and client receipt-recording endpoint. Invoice recipients come from authenticated merchant wallets.                                                                                                                    |
| High     | Browser storage and capped JSON files were treated as financial records.                                              | Added transactional SQL persistence, unique signatures, one confirmed receipt per invoice, idempotent transaction preparation, merchant isolation, pagination, audit events, and background recovery using on-chain tracking references. Old JSON files are preserved and are not imported as verified sales. |
| High     | Swap/yield checkout could transfer additional customer funds without acquiring the promised treasury asset.           | Invoice settlement now transfers the full invoice amount to the merchant in one transaction. Optional ExactOut swaps fund that transfer in the same transaction. Treasury allocation/withdrawal is a separate merchant-signed ExactIn swap, disabled by default.                                              |
| High     | The legacy Solidity proof check accepted a publicly reproducible hash; payment callbacks were insufficiently guarded. | Removed the deterministic bypass, added proof revocation, required settlement authority, guarded the payment entry point against reentrancy, validated tracks before storage, and snapshotted each request's allocation recipient. | Medium   | Financial metrics mixed balances, revenue, and invented earnings.                                                     | Revenue comes from verified invoices. Removed the fixed earnings rate, fake identity status, fabricated balances, and unsupported AI claims.                                                                |
| Medium   | Provider secrets, unrestricted API use, and weak request boundaries increased exposure.                               | Added server-only provider access, an authenticated production proxy, mutation origin checks, body limits, schemas, allowed RPC methods, security headers, safe error messages, request IDs, and rate limits. Vercel client-IP forwarding requires the proxy credential.                                      |
| Medium   | Build/deployment configuration and dependency sprawl obscured the active application.                                 | Reduced direct dependencies, replaced the unused authentication stack, rebuilt the lockfile with registry archive integrity data, corrected API output/start paths, separated legacy contract builds, and added CI and dependency update configuration.                                                       |

The API checks the **full** RPC genesis hash. CAIP network identifiers use a shorter prefix and must not be compared directly with `getGenesisHash`. Tests cover the distinction. See [Solana genesis definitions](https://github.com/solana-labs/solana/blob/master/sdk/src/genesis_config.rs) and [Solana network identifiers](https://solana.com/docs/payments/agentic-payments/x402).

## Launch requirements and remaining risks

1. **Resolve the exposed material.** Identify the authority and accounts associated with the historical keypair. Replace signing authorities wherever it still has privileges, and revoke or replace any still-valid exported credentials. A deployment keypair is not automatically the upgrade authority or a wallet holding funds; check actual on-chain roles. Coordinate any destructive history rewrite with repository collaborators. Deleting files is not rotation.
2. **Run external validation.** Complete a live dependency advisory scan, a clean CI build, the real PostgreSQL suite, browser/mobile wallet flows, and devnet invoice payments. Exercise RPC timeouts, failed transactions, rejected wallet prompts, reload after submission, and late receipts. Validate mainnet swap routes independently before enabling them.
3. **Provision production operations.** Set explicit network/RPC/origin configuration, private proxy/provider credentials, verified PostgreSQL TLS, a dedicated database role, backups, restore procedures, and monitoring. Run migrations explicitly before API startup. The supported API deployment is one process; horizontal scaling needs a shared rate-limit store and reconciliation coordination. Non-Vercel proxies need an equivalent trusted client-address integration to avoid grouping all users under the proxy's address.
4. **Keep treasury disabled until provider review is complete.** A checkbox acknowledges eligibility requirements; it does not verify identity, jurisdiction, investor status, or issuer approval. A configured mint is not independently authenticated by the application. Review the official mint, supported token program, routing/liquidity, price/fees/slippage, and acquisition/exit restrictions. Do not market this as issuer redemption or guaranteed earnings. [Ondo USDY product information](https://ondo.finance/usdy).
5. **Preserve invoice guarantees during provider upgrades.** Invoice swaps retain the V1 ExactOut contract. Jupiter's migration documentation says V2 `/build` supports ExactIn. V1 is a maintenance/provider-availability risk; a replacement must still guarantee the exact USDC invoice credit in one transaction. Direct USDC checkout remains the fallback. [Jupiter migration guide](https://developers.jup.ag/docs/swap/migration/metis-to-build).
6. **Handle financial exceptions before a commercial launch.** A database uniqueness constraint prevents duplicate revenue entries, not arbitrary duplicate transfers to a wallet. Different customers can sign different transactions for the same invoice before either finalizes. Additional transfers/overpayments need merchant investigation and a refund workflow; refunds and their accounting are not implemented. Cancelling an invoice with an existing payment attempt is intentionally refused, so abandoned attempts may need operational resolution. Late finalized payments are accepted and flagged rather than silently lost. An empty RPC address index does not automatically mark an attempt failed; unresolved attempts remain eligible for recovery. Monitor the reconciliation queue and provide an archival RPC provider and exception-handling process before scaling.
7. **Extend accounting deliberately.** Invoice revenue uses the invoice amount; it is not a complete accounting journal of every wallet transfer, fee, overpayment, refund, mark-to-market change, or taxable yield event. CSV export is paginated and labelled as a page export. Webhooks, team approvals, complete refund accounting, authenticated notifications, and automatic sweeps remain future work.
8. **Review legacy deployments separately.** The Solidity contracts only distribute native HSK and use an administrator-approved hash allowlist. They do not buy USDY or verify identity proofs. Existing deployments require a separate authority/bytecode review before use. The historical Rust workspace cannot be built as a program because its sources are absent.

Default development configuration is devnet and treasury trading is off. There is no claim that this audit makes the project ready to accept live customer funds.

## Final local verification

- 33 payment/API/shared tests passed; 5 legacy contract tests passed.
- Shared, API, and web TypeScript checks passed; shared and API builds passed.
- Production frontend compilation, type checking, page generation, and tracing passed with the documented temporary build settings.
- Windows and Linux/x64 clean-install simulations passed.
- Current source secret scanning, Git whitespace checks, and source file integrity checks passed.

No commit, deployment, funded payment, credential revocation, or Git history rewrite was performed.
